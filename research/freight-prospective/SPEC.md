# NS grain prospective experiment: coordinator specification v1

Status: implementable design for a local-only collector/forecast ledger, not implemented or activated. Consolidates qualified v002 and local v003; original worker drafts remain unchanged. Parameters below are proposed fixed research conventions, not measured optimal settings. Operational carload forecasting only; no stock-return claim.

1. Identity and immutable capture
Use only an official public STB NS workbook; retain original bytes, URL, retrieval-completed UTC, HTTP metadata and SHA256. Keep every version. Parse NS identity; Carloadings(Item11) sheet; E3/E4 native Sunday/Saturday dates exactly six days apart; B16=Grain, D8=Originated, D16 finite nonnegative integer carloads; independently verify unit/column meaning for each accepted template. Unknown/changed template or ambiguous dates => quarantine, never repair. No service metric substitute. Capture/public receipt time is known-by, not first-public publication. Never populate unknown original publication_at. Historical vintage_verified remains false.

Define version identity (official URL, SHA256). first_seen is immutable earliest successful local public-byte retrieval for that identity. Repeated identical GETs add sightings but never refresh first_seen. Retain parser version, source hash and validation result. Never physically discard an invalid revision.

2. Proposed cadence and deterministic selection
Public capture daily18:00UTC; forecast once per Thursday18:30UTC slot. No scheduler is started by this document. A future implementation must log missed capture/decision slots. A decision can begin within [18:30,18:45)UTC; otherwise skip. F is actual atomic forecast-decision creation time after source capture/parsing is complete, not nominal slot or receipt time. Freeze an ingestion snapshot as-of F; post-F arrivals cannot enter.

For each native week, consider only versions first_seen<=F. Sort by first_seen descending, then sourceSHA ascending, then URL ascending; choose the first. receipt_id is a content-derived deterministic key, not insertion-order randomness. If that selected version is invalid, quarantine that week; do not fall back silently to older valid bytes. Select the latest fully completed native week j represented as-of F; require its four consecutive weeks j-3..j all valid. Missing or invalid latest week blocks the forecast; do not search backwards for a convenient valid run. Newly revised valid bytes may be used in later decisions only.

Week end instant = Sunday00:00America/New_York immediately following its Saturday date. Require latest selected version's 0<=F-first_seen<=7*24hours AND 0<=F-week_end_instant<=14*24hours. All four version receipts<=F, all periods closed. Older lookback rows are exempt from latest freshness caps. Do not treat a repeated unchanged download as a new version or new freshness evidence.

3. Formula, target, schema and atomicity
P=(Cj+Cj-1+Cj-2+Cj-3)/4 in carloads. B=Cj. No estimation, calibration or threshold tuning. Target is [S,E), the first entire NY Sunday00-to-next-Sunday00 interval with S strictly after F; calendar conversion retains IANA zone and exact UTC bounds, including167/169hour DST weeks. No target whose start is past is eligible.

Store an immutable decision record: schema_version, protocolSHA, slotUTC, actualF_UTC, ingestion_snapshot_id, outcome/status(issued/skipped), reason_codes; four ordered inputs {operator,metric,units,week_start/end_dates,endUTC,value,sheet,value_cell,period_cells,URL,sourceSHA,version_first_seenUTC,receipt_id,parserSHA}; latest-age values; exact P and B; target local dates/zone/UTCstart/UTCend. No actual outcome embedded in original decision. Canonical JSON and contentSHA identify the record. Unique constraint(protocolSHA,slotUTC) AND(protocolSHA,operator,metric,target_startUTC,target_endUTC) for issued forecasts; one atomic insert transaction after validation. Any conflicting prior record stops insertion and logs duplicate-attempt separately, never overwrite. A skipped decision records evidence/reason without pretending to issue P/B.

4. Outcome policy
For a target, the primary actual is the first valid version of that exact NS native grain week whose immutable first_seen is after E and <=E+28*24hours. Choose minimum first_seen then SHA ascending then URL ascending; invalid candidates retained but ineligible. Freeze the chosen outcome in a separate hash-bound record; no replacement. Any later corrected version forms a separately labeled revision sensitivity, never rewrites primary errors. If no valid version by deadline, finalize missing/late and exclude from paired numerical scoring, retaining the attempted/issued target and reason. Lack of data is not zero volume. Keep target end/receipt timestamps distinct.

5. Scoring and partitions
At each deadline finalize targets in ascending target start (not arrival order); do not skip an unresolved earlier target when assigning scored indices. Primary paired absolute errors |P-Y| and |B-Y| in carloads on the identical scored target set; report both MAEs and their difference, plus all individual errors. No MAPE. First26 chronologically scored targets are descriptive development, next26 are untouched evaluation. No training/fitting or parameter tuning occurs in development. Freeze this protocol before any forecast; any change begins a separately named future experiment and cannot reuse evaluation as untouched. Report slot attempts, capture successes/failures, decisions skipped/issued, outcomes scored/missing/late/revised, reasons and date coverage for each partition. Require26scored targets and at least5distinct primary Y values per partition to report feasibility pass; these are operational gates, not statistical significance or generalizable alpha. Failing gates or worse MAE is retained as a negative result. Scored-target selection can bias results when missingness is informative; explicitly report excluded outcomes and avoid population/causal claims. No automatic continuation until favorable.

6. Accumulation and source limits
Current retained data: four nonconsecutive NS grain observations across2018/2023/2025 plus four service rows; zero current eligible lookback or forecasts. Need at least four consecutive valid completed native grain weeks captured before a real F, latest within both freshness caps, before the first issued forecast. Old rows are parser fixtures only, not backdated forecasts. Then52chronological scored nonoverlapping target weeks and5distinct outcomes in EACH26-target partition are required for this feasibility design; at least about a year after warm-up, longer for skips/missingness. Scoring may wait28days after final target closure. No promise weekly files remain available or complete. Original historical publication gaps are not cured by lag assumptions. A prospective known-by test needs immutable observed public bytes, not invented first-public dates.

7. Acceptance boundary
This document specifies deterministic behavior for future implementation. It is not tested software, a running collector, actual forecast or validated edge. A future implementation needs synthetic tests for version order/ties, invalid-revision quarantine, repeat-GET freshness, age-bound inclusivity, DST target selection, duplicate atomic inserts, missing outcomes and chronological scoring. All raw data remain local. No paid calls, trades, push or deployment authorized by this design.


Independent design review accepted this specification as implementable prose, not tested software. Clarification: latest week means latest represented closed native week, not necessarily latest calendar week; the14day cap allows publication lag. If a newly captured potential latest NS source cannot be assigned to a period because its template/period is ambiguous, block the decision until adjudicated rather than silently ignore it and fall back. Log that quarantine and its hash. Review identified no blocking design contradiction after consolidation.
